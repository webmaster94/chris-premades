## Required CPR correction

### Handle rider field deletion without dropping system riders

Files: `chris-premades/scripts/extensions/activities.js:2`, registered by `scripts/hooks.js:134`; exercise alongside `scripts/lib/utilities/itemUtils.js:172` and `scripts/extensions/effects.js:86`.

6.1 adds `Item5e.updateRiderFlags(changes)`. It combines riders from enchantment effects and activities whose metadata has `hasRiders`. It writes the field-deletion sentinel `_del` for an empty rider category, and runs after embedded effect creation, update, and deletion as well as during activity updates. The previous implementation only rebuilt the flag inside `preUpdateActivities` and omitted empty categories. [New updater and lifecycle calls](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/documents/item.mjs#L1164), [old activity updater](https://github.com/foundryvtt/dnd5e/blob/release-6.0.6/module/data/item/templates/activities.mjs#L425), [6.1 activity updater](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/data/item/templates/activities.mjs#L425).

CPR's `flagAllRiders` reads `flags.dnd5e.riders.activity` and spreads it with `...newRiders`. A deletion sentinel is not an iterable. A concrete trigger is an item with effect riders but no activity riders: the system sets `activity: _del`, and CPR's hook tries to spread it. An isolated execution of the actual local function with a symbol deletion marker reproduced **`TypeError: newRiders is not iterable`**.

Change the hook to distinguish arrays from field-deletion values, treating deletion as an empty activity list before merging CPR's hidden-activity IDs. Handle deletion of the entire `riders` parent too: replace that parent with an object before writing a nested activity field. Retain the system's effect-rider category and every system activity rider; do not replace the system's union with CPR-only IDs. Honor an explicit empty CPR hidden list so removed IDs do not return. Do not blindly carry old system riders forward, since the system may intentionally be removing them.

Validate an activity-only rider, an effect-only rider, both together, and deletion of the last rider. Repeat after creating, editing, and deleting an embedded enchantment effect. Include a CPR hidden activity in those cases and confirm it stays hidden without resurrecting deleted system riders. This is a source-level reproduction, not a completed Foundry integration test.

## Other relevant behavior and bounded follow-up

- **Activity subclasses:** `getByType(type)` now includes types whose `metadata.like` matches, by default. `{like:false}` requests exact types. CPR calls it in `scripts/lib/utilities/itemUtils.js:6,191`, `scripts/native/macros/generic/bladeSpell.mjs:15,36`, and other weapon/spell macros; GPS has no direct calls. These callers consume the corresponding attack/save/enchant interface, so the broader result does not establish a failure. Keep the default unless a caller specifically requires an exact type; test a custom attack-like activity before declaring support. [Collection implementation](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/data/fields/activities-field.mjs#L96).
- **Antimagic:** 6.1 moves `magicAvailable` to the base item model and checks the actor's `antimagic` status. `Activity.canUse` delegates to `!isHidden`, which includes `visibility.requireMagic`. CPR's `canUsePatch` at `scripts/extensions/activities.js:77` returns `true` for a CPR hidden activity without these checks. Preserve this intentional rider bypass while rejecting `visibility.requireMagic && item.system.magicAvailable === false`, and retaining item usability restrictions. This matters for magic-required hidden activities inside the new region. CPR's general `scripts/lib/utilities/activityUtils.js:125` also only tests consumption; callers that use it as full usability should respect the system result. Do not treat all hidden activities as unusable, since CPR deliberately invokes riders. [Magic availability](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/data/abstract/item-data-model.mjs#L146), [activity visibility](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/documents/activity/mixin.mjs#L109). The `ActiveEffect.isSuppressed` magic check already existed in 6.0.6; it is not a newly removed API.
- **Enchantments:** 6.1 adds `system.rider.activities/effects/items`, retaining activity-profile riders. CPR's `scripts/lib/utilities/itemUtils.js:87` instead writes the old `flags.dnd5e.enchantment.riders` and `transfer:false`. This is a pre-existing issue, not proven breakage introduced by 6.1: even 6.0.6's collector reads the activity profile rather than those flags. For a separate cleanup, use proper applied-enchantment data, including `transfer:true`, `system.origin`, and the documented rider fields; do not silently equate old flag keys with the new schema. [6.0.6 collector](https://github.com/foundryvtt/dnd5e/blob/release-6.0.6/module/data/active-effect/enchantment.mjs#L254), [6.1 collector](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/data/active-effect/enchantment.mjs#L284).
- **Damage bypasses:** new rules feed `DamageRoll.options.applicationOptions`, message application options, and ignore/downgrade sets into damage application. `calculateDamage` gains `potential` details and special resistance categories. GPS `scripts/automations/raceFeatures/furyOfTheSmall.js:72` already calls the system calculator with cloned calculation options, and neither repo reads the changed `active.all` shape. No direct GPS fix demonstrated. Test this bonus with resistance, immunity downgrade, and mixed damage once the separate Midi upgrade supplies the new options correctly. [Applied rules](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/documents/applied-rules.mjs), [damage message](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/data/chat-message/damage-message-data.mjs), [actor calculation](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/documents/actor/actor.mjs#L840).
- **Summons and delayed actions:** summon damage bonuses now use rule changes conditional on activity type; applied summon effects resolve origin/target references. Subsequent actions rebuild their activity from current item data and consumption/scaling flags. No removed method used by either repo was found. Check a summon with both attack and save damage, and an upcast delayed damage button, without duplicating bonuses the system now supplies. [Summon source](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/documents/activity/summon.mjs#L408), [subsequent actions](https://github.com/foundryvtt/dnd5e/blob/release-6.1.0/module/documents/activity/mixin.mjs#L309).
